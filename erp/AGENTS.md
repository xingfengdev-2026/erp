# Repository Guidelines

## Project Structure & Module Organization

This repository contains `erp` (easy-to-use reverse proxy), a Rust-based reverse proxy tool. Keep the layout simple and predictable:

- `src/main.rs` contains the current v1 CLI, config loading, authentication, and forwarding implementation.
- `examples/` contains raw and AES TOML configuration examples.
- `docs/` contains project plans and design notes.
- `.github/workflows/` contains CI and release automation.
- `target/` is generated by Cargo and must stay untracked.

The current implementation plan lives in `docs/PLAN.md`.

## Build, Test, and Development Commands

Use Cargo commands once the Rust project is initialized:

- `cargo run -- server --config server.toml`: run server mode.
- `cargo run -- client --config client.toml`: run client mode.
- `cargo run`: start interactive role selection when no role is provided.
- `cargo test`: run unit and integration tests.
- `cargo fmt --check`: verify formatting.
- `cargo clippy -- -D warnings`: run lint checks.
- `cargo build --release`: build an optimized binary.
- `.\scripts\build-local.ps1`: build local Windows and Linux compatibility artifacts into `dist/`.
- `.\scripts\deploy-test-remote.ps1`: upload the local Linux artifact to `user@example.com` and run `erp --version`.

## Coding Style & Naming Conventions

Use standard Rust formatting with `rustfmt`. Prefer small modules with clear ownership boundaries. Use `snake_case` for functions, variables, modules, and file names; use `PascalCase` for types and traits; use `SCREAMING_SNAKE_CASE` for constants. Keep configuration field names lowercase with underscores in TOML, for example `control_port`, `remote_port`, and `udp_mode`.

## Testing Guidelines

Add tests for every behavior that affects forwarding, authentication, encryption, cleanup, or configuration loading. Unit tests should live near the module under test. End-to-end scenarios should live in `tests/`. Cover TCP forwarding, UDP direct forwarding, UDP-over-TCP forwarding, AES mode, raw mode, duplicate port rejection, invalid token rejection, and interactive role/config selection.

## Commit & Pull Request Guidelines

Use concise Conventional Commit-style messages, such as `feat: add tcp forwarding` or `fix: reject duplicate remote ports`. Pull requests should include a short summary, test results, linked issues when relevant, and screenshots or terminal output for CLI behavior changes.

## Security & Configuration Notes

All transport modes require token authentication. The token must never be sent directly over the network or written to logs. Use challenge-response authentication with a server nonce and HMAC proof. Treat `raw` mode as suitable only for trusted networks or debugging. Prefer `aes-256-gcm` when traffic should not be visible on the wire.
